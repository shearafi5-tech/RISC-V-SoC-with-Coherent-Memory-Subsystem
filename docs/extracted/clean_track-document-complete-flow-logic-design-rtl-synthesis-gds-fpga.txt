What to Pursue

 1. Design the ALU logic on paper. Write the truth table / gate logic for all RV32I ALU operations (ADD, SUB,
    AND, OR, XOR, SLT, SLL, SRL, SRA). Identify the critical path (SUB with SLT is typically longest).
? 2. Design the cache FSM on paper. Draw the state diagram for the D-cache manager (states: IDLE, CHECK,
    HIT, MISS, AXI_AR, AXI_R, FILL, AXI_AW, AXI_W, AXI_B, INVALIDATE). This is the heart of the system.

 3. Design the coherence controller FSM on paper. Draw the state diagram for tracking I/S/M across two
    cores and dispatching invalidations.

 4. Design the arbiter logic. A round-robin arbiter for 2 masters -- draw the truth table and priority logic.
 5. Draw the system block diagram. Show all modules, data paths, control signals. This becomes the RTL

    architecture.
 6. Sketch the memory map. Decide addresses for shared SRAM, MMIO, UART, GPIO.

Exit Criteria

          ALU logic table complete (all 10+ operations)
          D-cache FSM state diagram drawn
          Coherence controller FSM state diagram drawn
          Arbiter logic designed
          System block diagram drawn
          Memory map defined

    Transparency note: Skipping this stage and jumping to RTL is the #1 reason students produce buggy,
    un-synthesizable code. The FSM designs here are what you translate directly into SystemVerilog

    always blocks. Get them right on paper first.

?Detailed build tasks:

 1. alu.sv -- Combinational ALU. Parameterized width (default 32). All RV32I operations. Zero/compare

     flags.

 2. reg_file.sv -- 32x32-bit register file. 2 read ports, 1 write port. x0 always zero. Synchronous write,

     combinational or sync read (decide based on single-cycle timing).

 3. control_unit.sv -- Instruction decoder. Decodes 32-bit instruction to control signals (ALU op, reg

     write, mem read/write, branch, etc.).

 4. rv32i_core.sv -- Integrate ALU + reg file + control unit + PC logic + data memory interface. Single-

     cycle: every instruction completes in 1 clock.

 5. sram_reg_array.sv -- Generic parameterized register array (depth, width configurable). Used for I-

     SRAM and shared SRAM. Synchronous read, synchronous write.

 6. d_cache.sv -- Cache line storage (valid, tag, data, state). Direct-mapped. Parameterized line count.

 7. d_cache_mgr.sv -- Cache controller FSM. Handles hit/miss, AXI-Lite master interface, coherence

     invalidation interface. This is the most complex module -- give it the most attention.

 8. coherence_ctrl.sv -- Tracks per-line, per-core state. On write_notify from one core, invalidates the

     other core's line. Maintains status/counters for MMIO.

 9. axi_lite_arbiter.sv -- Round-robin arbiter for 2 masters. Grants bus access; ensures one

     transaction at a time per arbitration cycle.

10. axi_lite_decoder.sv -- Address decode to route to shared SRAM / MMIO / UART / GPIO. Returns

     DECERR for unmapped.

11. mmio_regs.sv -- AXI-Lite slave. Readable coherence status, event counters, doorbell, control.

12. uart_core.sv -- AXI-Lite slave. TX with baud generator, RX with baud sampler. 8N1.

13. gpio_led.sv -- Simple AXI-Lite slave, single output register for LEDs.

14. riscv_soc_top.sv -- Integrate everything. Instantiate 2 cores, 2 I-SRAMs, 2 D-cache managers, 1

     coherence controller, arbiter, decoder, shared SRAM, MMIO, UART, GPIO. Wire all signals. Reset
     synchronizer.

15. Yosys smoke test -- Run Yosys synthesis on the top module ASAP (even before verification is complete).
     Catch unsynthesizable constructs early.

RTL Coding Standards

· Use always_ff @(posedge clk or negedge rst_n) for all flops.                            comb .
· Use always_comb / assign for all combinational logic. Never always @(*) without
· No initial blocks in synthesizable RTL (only in testbenches and memory init wrappers).
· No $display , $finish in synthesizable code.
· No delays ( #10 ) in synthesizable code.

· Every signal has a defined reset value.
· Parameters for all widths/depths -- no magic numbers.

Exit Criteria

All RTL modules written and individually compileable

rv32i_core passes a simple instruction test in isolation
d_cache_mgr passes a simple hit/miss test
coherence_ctrl passes a simple invalidate test
?riscv_soc_top compiles and Yosys synthesizes (smoke test)

No inferred latches (check Yosys warnings)

Concepts to Deal With

Concept                           Why it matters

models)

UVM methodology

Code coverage                     Coverpoints for coherence states, events, hit/miss, error.
                                  Line, toggle, branch, FSM state coverage. Identify untested code.
Assertions (SVA)                  Immediate/concurrent assertions for protocol checking (AXI handshake, coherence
                                  invariants).
Constrained-random verification   Randomize addresses, data, timing to stress the design.

What to Pursue

4.1 Directed Self-Checking Testbench ( tb_directed.sv ):

Test cases in order:

 1. Reset test: Assert rst_n=0 , check all state = I, PC = RESET_PC, counters = 0.

 2. Single-core memory access: Core 0 writes shared addr, reads back, asserts value matches.
 3. Cache hit: Core 0 loads addr A twice; second access is a hit (check hit counter increments).
 4. Cache miss: Core 0 loads addr A first time; miss counter increments.
 5. Cross-core coherence (THE key test): Core 0 writes addr A; check Core 1's line for A becomes I; Core 1

     reads A, gets new value.
 6. Stale data prevention: Verify Core 1 does NOT get old value after invalidation.
 7. Simultaneous write: Both cores write same addr same cycle; check deterministic winner; final SRAM value

     correct.
 8. No-cached-copy: Core 0 writes addr that Core 1 never loaded; no invalidation needed; check no spurious

     invalidate.
 9. Error/unmapped access: Core accesses unmapped address; check DECERR/SLVERR response.
10. Counter verification: Check INV_COUNT, HIT_COUNT, MISS_COUNT match expected after test sequence.

4.2 UVM Environment:
?                                          uvm_test_top

                                          Environment

Coherence Monitor                                             Virtual Sequencer

Functional Coverage                       Core 1 Sequences    Core 0 Sequences

                     Shared SRAM Monitor  AXI Master Agent 1  AXI Master Agent 0
                                          Core 1 path         Core 0 path

                                                                                                                              Scoreboard

UVM components to build:

  · axi_lite_master_agent -- driver + sequencer + monitor. Drives AXI-Lite transactions.
  · axi_lite_seq_item -- transaction object (addr, data, we, wmask, response).
  · core0_seq , core1_seq -- constrained-random read/write sequences to shared addresses.
  · coherence_vseq -- virtual sequence coordinating both cores for coherence scenarios.
  · shared_sram_scoreboard -- predicts expected SRAM content; compares with monitor

    observations.

  · coherence_monitor -- observes invalidation events; checks: every cross-core write must produce

    an invalidation.

  · coverage_collector -- covergroups for: coherence state per line per core, hit/miss, invalidation

    count, simultaneous-write, error response.

  · axi_lite_if -- SV interface connecting UVM to DUT.

Assertions (SVA) to include:

   // AXI-Lite handshake: valid stays until ready
   assert property (@(posedge clk) disable iff (!rst_n)

     awvalid |-> awvalid until awready);
   // Coherence invariant: after write_notify, inv_req must fire within 2 cycles
   assert property (@(posedge clk) disable iff (!rst_n)

     write_notify |-> ##[1:2] inv_req);
   // No two masters granted simultaneously
   assert property (@(posedge clk) disable iff (!rst_n)

     !(grant0 && grant1));

Exit Criteria

          Directed TB: all 10 test cases pass, self-checking (no manual waveform inspection needed)
          UVM: scoreboard passes for 1000+ random transactions
?Functional coverage at least 90% on coherence states, hit/miss, invalidation, error
Code coverage at least 90% line, at least 80% toggle/branch
All assertions pass (0 failures)

What to Pursue

The OpenLane flow runs these stages automatically. Your job is to configure, monitor, and fix issues:
 1. Floorplan stage:

       Set core utilization to ~55% (leave room for routing).
       If using SRAM macros: place macros first, then let OpenROAD place std cells.
       Check: core area reasonable, pin placement OK.
 2. Power plan stage:
       OpenLane generates a power grid automatically (VDD/VSS rings + stripes).
       Check: grid coverage adequate, no IR-drop hotspots (OpenROAD reports this).
 3. Placement stage:
       Check: placement congestion, placement density per region.
       If congestion > 95% in any region, increase core area or reduce utilization.
? 4. CTS stage:
       Check: clock skew (should be less than ~10% of clock period), max transition.
       If skew too high, adjust CTS buffers/config.

 5. Routing stage:
       Check: DRC violations (must be 0), routing congestion.
       If DRC violations, fix (usually means floorplan or placement issue).

 6. Sign-off stage:
       Run DRC (Magic) -- 0 violations required.
       Run LVS (Netgen) -- netlist match required.
       Capture layout screenshot (KLayout GDS view).

Exit Criteria

          OpenLane flow completes end-to-end
          DRC: 0 violations
          LVS: clean (netlist match)
          Timing: WNS >= 0 (setup met), hold met
          All reports captured
          Layout screenshot captured (KLayout)

Transparency note: If timing doesn't close at 20 MHz, check the critical path. In a single-cycle RV32I
core, the critical path is almost certainly ALU to register file write or the cache tag comparison to AXI
path. If it's the ALU, consider lowering the clock target. If it's the cache/coherence path, check for
unnecessary combinational depth.

fixing them in Stage 5. This is why the brief says "understand it completely" first.

12. Learning Outcomes (what you should know after completing this
track)

After completing this project, you will have demonstrated understanding of:

          RISC-V ISA and single-cycle processor design
          Cache hierarchy fundamentals (direct-mapped cache, hit/miss, write-through)
          Cache coherence concepts (I/S/M states, invalidation-based coherence)
          Bus protocols (AXI4-Lite: 5-channel handshake, arbitration, address decoding)
          SystemVerilog RTL design (synthesizable coding, FSMs, structured types)
          Verification methodology (directed TB, UVM, coverage, assertions)
          ASIC synthesis flow (Yosys, technology mapping, SDC)
          ASIC physical design flow (floorplan, PDN, placement, CTS, routing, sign-off)
          DRC/LVS sign-off
          FPGA implementation flow (Vivado, BRAM, MMCM, constraints, bitstream)
          System integration (multi-core, shared memory, peripherals)
          Documentation and reproducibility

This is a full-stack IC design project -- from logic gates to silicon to working FPGA hardware. The coherence
subsystem is what makes it more than a "two cores and a memory" exercise.
