0. What this document is

A frank, expert read-through of the project brief plus a concrete module spec and day-by-day plan, locked to
the chosen toolchain. No fluff -- the goal is that after reading this you understand the scope precisely and can
execute without surprises.

1. The one-sentence essence

    Build two simple RV32I cores that share one data memory through a simplified invalidation-based
    coherence mechanism, wrap it on an AXI4-Lite bus, simulate it (directed + UVM), synthesize it, run it
    through OpenLane physical design on sky130A, and boot it on an FPGA that shows coherence events
    on UART/LEDs.

5. The coherence model (what they actually want)

They explicitly say: "A complete industry-level coherence protocol is not required." Do NOT implement
MESI/MOESI snooping. Build the minimal mechanism:

       SRAM)  reload on next accreesms ote write invalidates this

                                                             copy

                                                                   remote write invalidates

                               S                                   (writeback optional,

                                                                   write-through avoids it)

              core writes its own line

                                                                            M

Three states: I (Invalid), S (Shared/clean), M (Modified, this core owns it). On a write by core A:
  · Core A  line M, writes shared SRAM (write-through).
  · Coherence controller signals core B: "invalidate line X."
  · Core B marks its copy I  next read refetches the updated value.

That single flow is the entire "demonstrate coherence" requirement.

6. What the brief deliberately excludes

    "Pipelining, advanced cache hierarchies, and scalable multi-core coherence protocols are not required."

  · No pipeline -- single-cycle core. Don't build a 5-stage pipeline.
  · No L2 / multi-level cache. One tiny private cache per core.
  · No scalable snooping/directory bus. Two cores, hardwired invalidate.
  · No interrupts/exceptions/privileged CSRs beyond debug regs. RV32I base has no CSR instr.
  · No DRAM controller -- SRAM only.
Effort spent on excluded items is wasted.

8. Physical design on sky130A / OpenLane -- the part most students
underestimate

OpenLane flow = Yosys synthesis  OpenROAD floorplan  powerplan  placement  CTS  routing 
sign-off (DRC/KLayout LVS). Concrete reports you must produce:

  · SDC -- clock definition + I/O delays. Realistic sky130 target: start at 20 MHz (50 ns period), tighten toward
    40-50 MHz if timing closes. Don't chase 100 MHz in sky130.

  · Floorplan  core utilization ~50-60% (leave room for routing on a small design).
  · Power plan  standard ring + stripes; sky130 metal stack (M1-M5/M6).
  · Placement  CTS  routing.
  · Reports required: area, timing (setup/hold WNS/TNS), power, congestion, DRC clean, LVS clean, final

    layout screenshots.

sky130 / OpenLane-specific gotchas:

  · SRAM macros: OpenLane supports OpenRAM for generating SRAMs. For tiny sizes (shared data SRAM, I-
    SRAMs) you can either (a) generate an OpenRAM macro, or (b) use a register-array / flip-flop-based
    memory which is fully synthesizable and avoids macro/integration pain. For a 5-day project, recommend
    register-array for I-SRAM (small, e.g. 1-4 KB) and a small OpenRAM macro OR register array for shared
    data SRAM. Register arrays close timing fine at 20-40 MHz.

  · Don't infer latches -- Yosys will warn; OpenROAD sign-off DRC may flag them.

  · Async reset -- infer properly ( always @(posedge clk or negedge rst_n) ); sky130 sc_hd

    has proper reset flops.
  · Black-box RAMs -- if using OpenRAM macros, you must provide a Liberty/LEF for them to OpenLane; if

    using register arrays, no black-boxing needed.
  · Run a synthesis smoke test as soon as top RTL exists (day 2-3) so day 5 isn't the first time tools see your

    design.

9. FPGA demo -- what "demonstrate" concretely means

The grader wants to see coherence happen:

  · Core 0 writes a known value to shared addr X (LED/UART: "C0 write X").
  · Coherence event fires (LED pulse / UART: "INVALIDATE  C1").
  · Core 1 reads X and gets the new value (LED/UART shows it).
  · A stale read fails the demo -- so it doubles as a live self-check.

UART > LEDs alone -- UART logs the sequence. Use both: LEDs for heartbeat/event, UART for values.

14. The transparent warnings (what the brief doesn't say)

  · Coherence only fixes future loads. If core B already has a value in a register, invalidating its cache line
    does nothing. The demo program must re-read after the invalidation. Design demo SW around this. #1
    silent bug.

  · "Simultaneous writes" need a deterministic arbiter winner + loser invalidation. Brief lists it as a test case.
  · Instruction fetch must NOT go through the coherence path -- only data is shared; I-SRAMs are private.
  · Reset behavior: all caches  Invalid, all state  known. Directed reset test is required.
  · "Error conditions": define yours (bus error/SLVERR, unmapped access) and handle them -- or UVM

    coverage exposes the gap.
  · Coverage is a deliverable: code coverage + functional coverage. Add coverpoints for coherence states

    and events.

  · AXI4-Lite is not AXI4. No bursts, no wlast / rlast , no awlen / awsize / awburst . Keep it

    strictly Lite -- 5 channels, one transaction at a time per channel. Don't over-engineer.

  · OpenLane RAM macros: if you go OpenRAM, you must supply .lib + .lef + .gds to the flow and

    black-box in Yosys. Register arrays avoid all of this. Decide early.

16. Bottom line

  · Scope: two small RV32I cores + tiny private caches + a 3-state invalidate-on-write coherence link + one
    shared SRAM on AXI4-Lite, verified three ways, pushed through Yosys/OpenLane on sky130A, shown on
    FPGA.

  · Intellectual center of gravity: the coherence controller + the demo proving stale data gets invalidated.
  · Schedule risk centers: day 1 (CPU), day 5 (back-end). Mitigated by reusing a clean core + early synth

    smoke test.
  · The brief gives you permission to stay small. Use it. Small + correct + fully-verified + cleanly-physical-

    design'd beats big + half-finished every time.
